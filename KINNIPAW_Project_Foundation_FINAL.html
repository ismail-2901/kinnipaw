2. Product definition

2.1 Product summary

KINNIPAW is a responsive web platform and companion mobile application for animal guardians and animal-welfare communities. It combines social discovery, animal identity and care records, adoption workflows, lost-and-found reporting, rescue coordination, direct communication, reminders, professional discovery, notifications and carefully bounded AI assistance.

2.2 Product principles

  1. Animal welfare first: engagement mechanics must never reward dangerous, exploitative or misleading behaviour.
  2. Trust by design: verification, reporting, moderation, privacy controls and audit trails are core product capabilities.
  3. Useful before clever: AI is optional assistance, never a substitute for veterinary judgement or emergency services.
  4. Mobile-first, not mobile-only: every key workflow works on small screens and desktop.
  5. Inclusive by default: Bangla and English, accessible controls, low-bandwidth resilience and clear language.
  6. Privacy and safety: do not expose precise home locations, private contact details or sensitive records by default.
  7. Incremental architecture: start with a modular monolith and evolve only when measurable scale requires it.

2.3 Primary user journeys

  • Visitor → browse public community/adoption content → register → create profile → add an animal profile.
  • Owner → create animal profile → upload photos → record care events → schedule reminders → receive notifications.
  • Owner/community member → publish post → react/comment/bookmark/follow → report unsafe content if needed.
  • Adopter → search adoption listings → review details → submit application → communicate → track status.
  • Reporter → publish lost/found report → add sightings and evidence → receive possible matches → coordinate safe contact → mark resolved.
  • Rescuer → create rescue request → volunteers offer help → assignment and status updates → close with outcome.
  • Professional → submit verification information → admin review → publish approved profile/services.
  • Moderator → review queue → investigate report → take proportionate action → record audit event.

3. Complete product scope

3.1 Identity and account

  • Email/password and supported OAuth sign-in where configured; secure session management; password reset; email verification.
  • User profile, avatar, display name, bio, locale, notification preferences and privacy controls.
  • Account deletion/export request workflow and consent records.
  • Role assignment controlled by trusted administrative workflows, never by client-submitted role fields.

3.2 Animal profile management

  • Multiple animal profiles per owner; species, breed, name, age/date of birth, sex, size, colour, description and optional identifiers.
  • Animal photo gallery and ownership/visibility settings.
  • Health timeline: vaccinations, medications, allergies, vet visits, weight and care notes.
  • Reminders for vaccinations, medication, grooming and other owner-defined care tasks.
  • Clear distinction between user-entered records and professionally verified records.

3.3 Social community

  • Feed, posts, image/media attachments, comments, reactions, bookmarks, follows and hashtags.
  • Community groups, membership, group posts and group moderation.
  • Search and discovery with pagination, filtering and safe defaults.
  • Content reporting, block/mute controls and moderation status.

3.4 Adoption

  • Adoption listings with animal details, location at an appropriately coarse level, eligibility and adoption requirements.
  • Search, filters, saved searches and listing status.
  • Applications, applicant questions, review, decision, status history and safe communication.
  • Responsible-adoption guidance and anti-scam warnings.

3.5 Lost and found

  • Lost/found reports, description, last-seen/found time, approximate location, photos and safe contact method.
  • Sightings with timestamps and optional evidence.
  • Potential match records with confidence, explanation, review state and algorithm version.
  • Reporter confirmation and resolved/closed workflow.
  • Never publish exact private addresses or expose a reporter's live location by default.

3.6 Rescue coordination

  • Rescue requests with urgency, description, approximate location, evidence and status.
  • Volunteer offers, assignment, progress updates, handoff and closure outcome.
  • Abuse prevention, duplicate detection and transparent status history.

3.7 Messaging and notifications

  • One-to-one conversations and conversation membership.
  • Text messages initially; media sharing only after secure upload and moderation controls are in place.
  • In-app notifications and configurable email/push channels where provider credentials and platform support exist.
  • Read state, mute/block, report and rate-limit controls.

3.8 Professional discovery and events

  • Veterinarian/clinic/service-provider profiles, verification status, services, location and contact details.
  • Community events and educational sessions can be added as a controlled module after core workflows.
  • No invented ratings, credentials or medical claims; verification provenance must be visible.

3.9 Admin and moderation

  • Role-based admin dashboard, user and professional verification, content/report queues, adoption/rescue oversight and system configuration.
  • Moderation actions with reason, actor, target, timestamp and appeal/review path where appropriate.
  • Audit logs for sensitive administrative and security actions.
  • Least-privilege access; support staff must not receive unrestricted access to private user data.

3.10 Explicitly out of scope for initial release

  • Online payments, escrow, insurance, pharmacy sales or marketplace checkout.
  • AI veterinary diagnosis, prescription, emergency triage decisions or autonomous treatment advice.
  • Public real-time tracking of animals or users.
  • Unmoderated anonymous chat, public exposure of private phone numbers, or unrestricted user-to-user file uploads.
  • Complex microservices, Kubernetes or paid infrastructure before actual demand justifies them.

5. System architecture

5.1 Architecture style

Use a modular monolith with clear domain boundaries. Web and mobile are separate clients consuming the same versioned API and shared contracts. PostgreSQL is the source of truth. Do not split into microservices until independent scaling, deployment or team ownership is demonstrably necessary.

5.2 Logical modules

  • Identity & Access
  • User Profiles
  • Animal Profiles & Care
  • Community & Feed
  • Adoption
  • Lost & Found
  • Rescue Coordination
  • Messaging
  • Notifications
  • Professional Directory
  • AI Assistance
  • Administration & Moderation
  • Audit & Platform Operations

5.3 Dependency direction

UI → application/use-case layer → domain logic → repository/API interfaces → infrastructure adapters. Domain logic must not depend on Next.js, React Native, Supabase SDK internals or UI components. Shared packages must remain platform-neutral.

5.4 Data flow

  1. Client validates input for usability.
  2. API authenticates the session and derives the actor identity from verified credentials.
  3. Authorization checks role, resource ownership, relationship and resource state.
  4. Input is validated again at the server boundary.
  5. Business rules execute in a transaction where multiple writes must remain consistent.
  6. Database constraints and RLS provide defence in depth.
  7. Response returns a stable DTO; sensitive columns are never serialized by default.
  8. Important state changes emit notifications and audit events through a reliable queued/outbox-style mechanism when required.
Schema compatibility note: Legacy database identifiers such as pet_photos and pet_health_records are retained in the initial inventory to avoid unreviewed migration churn. Their domain meaning is animal-inclusive; any rename requires an approved migration decision and compatibility plan.

6.1 Relationship summary

  • Auth identity 1:1 profiles; profile 1:N animals, posts, reports, messages and notifications.
  • Animal 1:N photos, health records, vaccinations, medications and reminders.
  • Post 1:N media/comments; posts N:M hashtags; users N:M posts via reactions/bookmarks.
  • Users N:M users via follows; users N:M groups via group_members.
  • Adoption listing 1:N applications and status history.
  • Lost/found report 1:N sightings and N:M candidate matches through lost_found_matches.
  • Rescue request 1:N assignments/progress events (if progress events are needed, add a dedicated table only after documenting the schema change).
  • Conversation N:M profiles via conversation_members; conversation 1:N messages.
  • Reports may target supported content/resource types; moderation actions reference report and target.
  • Roles N:M permissions through role_permissions.
Schema decision to resolve before migration: Earlier planning referenced both lost_found_matches and ai_match_candidates. This baseline includes lost_found_matches as the canonical persisted match entity. Do not silently create a second overlapping table. Decide whether AI candidate output is transient or whether it needs a separate table, document the decision, update ERD and API, then migrate.

6.2 Database standards

  • Foreign keys and unique constraints enforce invariants; do not rely only on UI validation.
  • Indexes for foreign keys, feed ordering, status filters, owner lookups, search filters and notification unread queries.
  • Use cursor pagination for feeds and large collections; avoid unbounded queries.
  • Use soft deletion only where recovery, moderation or legal requirements justify it; define retention and hard-delete process.
  • Use PostGIS only if precise geospatial search is justified and supported; store public location at a privacy-safe granularity.
  • All schema changes must be versioned SQL migrations with rollback/recovery notes and backup considerations.

7.1 Authorization rules

  • Visitor is an unauthenticated state, not a database role.
  • Member is the default authenticated role. Professional is an additional verified capability, not a blanket privilege escalation.

  • Use RLS for user-scoped tables; test both allowed and denied paths for every policy.

9. Security architecture

9.1 Authentication and sessions

  • Use the managed auth provider securely; verify tokens server-side and validate issuer/audience/expiry.
  • Use secure, HttpOnly, SameSite cookies for web sessions where applicable; protect state-changing requests against CSRF according to the chosen auth flow.
  • Mobile tokens must use secure platform storage; never AsyncStorage for long-lived secrets.
  • Implement email verification, password reset protections, session revocation and rate limits.

9.2 Authorization and data isolation

  • Enable RLS on every exposed user-data table and write explicit policies for SELECT/INSERT/UPDATE/DELETE.
  • Default deny. Test owner, non-owner, anonymous, blocked user, moderator and admin scenarios.
  • Never ship service-role or privileged database keys to browser/mobile bundles.
  • Do not trust client-supplied user IDs, roles, ownership, prices, status transitions or verification flags.

9.3 Input, uploads and abuse

  • Validate every request at the server boundary with allowlisted schemas and bounded lengths.
  • Restrict uploads by MIME sniffing, extension, file size and image dimensions; re-encode images where practical; store outside executable paths.
  • Rate-limit login, password reset, posting, comments, messages, reports, search and AI endpoints.
  • Protect against XSS, SQL injection, CSRF, SSRF, IDOR/BOLA, mass assignment, open redirects and insecure direct object references.
  • Use safe rendering for user-generated content; sanitize rich text and never render arbitrary HTML.

9.4 Privacy and safety

  • Collect the minimum personal data required. Make profile, animal, post and location visibility explicit.
  • Approximate public location; keep exact contact/location details private and share only with consent or legitimate workflow access.
  • Provide block, report, mute, content removal and appeal/review mechanisms.
  • Define retention/deletion for messages, reports, AI prompts, health data and audit records.
  • Do not send sensitive personal data or private conversations to an AI provider without clear disclosure, consent and minimization.

9.5 Operational security

  • Secrets in environment variables/secret manager only; maintain separate development, preview and production credentials.
  • Rotate leaked credentials immediately; never commit .env files.
  • Dependency scanning, lockfile review, CI checks, database backups and restore drills.
  • Audit privileged actions; restrict access to logs; do not log passwords, tokens, private messages or full health records.

10.1 AI engineering requirements

  • Use provider abstraction so models can be changed without rewriting domain logic.
  • Keep prompts/version identifiers, provider/model metadata, latency, token/cost estimates and safety outcomes; minimize or redact raw user content.
  • Use deterministic rules for permissions, eligibility, status transitions and safety-critical workflows; AI must not decide authorization.
  • Apply timeouts, retries with limits, rate limits, output validation and fallback messaging.
  • AI calls must be opt-in where personal data is involved and must disclose limitations.
  • Never hardcode paid API assumptions. Provide a no-AI fallback for core workflows.

12. Performance, scalability and quality engineering

12.1 Performance goals

  • Set measurable Core Web Vitals targets; aim for LCP ≤ 2.5s, INP ≤ 200ms and CLS ≤ 0.1 at the 75th percentile when sufficient real-user data exists.
  • Optimize images, responsive sizes, lazy loading, font subsets and route-level code splitting.
  • Use server rendering for indexable public content and avoid unnecessary client components.
  • Use cursor pagination, indexed filters, bounded queries and caching with explicit invalidation.
  • Debounce search; cancel stale requests; avoid N+1 queries; inspect query plans for slow database paths.
  • Keep mobile bundles lean; test on low/mid-range Android devices and slower networks.

12.2 Testing strategy

  • Unit tests: domain rules, validators, permission decisions, status transitions and utility functions.
  • Integration tests: API handlers, database constraints, RLS and storage access.
  • Component tests: forms, dialogs, navigation, empty/error/loading states.
  • E2E tests: sign-up, animal creation, post creation, adoption application, lost/found report, rescue workflow, messaging and moderation.
  • Security tests: IDOR/BOLA, privilege escalation, RLS bypass, upload abuse, rate-limit bypass and secret leakage.
  • Responsive/accessibility tests across key viewport sizes, keyboard navigation and screen-reader labels.

Mandatory task loop

  1. Read AGENTS.md, relevant source docs, canonical specs and exact task ID.
  2. Inspect Git status, existing code, environment and dependency versions.
  3. State acceptance criteria, plan, dependencies, risks and affected data/API/permissions.
  4. Implement only the current task in a small diff.
  5. Add unit, integration, RLS/authorization and E2E tests as appropriate.
  6. Run format, lint, typecheck, tests, migration validation and production build relevant to the scope.
  7. Review diff, secrets, dependencies, performance, accessibility and security.
  8. Update docs, task status and traceability with evidence.
  9. Stop on any failed gate. Fix and rerun before starting the next task.
  10. Report exact changed files, commands, pass/fail results, untested areas and blockers. Never say “bug-free” or “100% secure” without defensible evidence.
Human approval checkpoints: brand/legal clearance; architecture/cost changes; destructive migrations; handling sensitive personal/animal-health data; external AI providers; production secrets; account billing; public release; app-store submission. The agent may prepare and explain these steps but must not make irreversible or paid decisions autonomously.
